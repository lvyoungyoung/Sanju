# 句子生成与分类、用途生成的耗时对照

## 对照方式

- 方案一：一次 MiMo 请求生成两组三句、中译，以及每句分类和表达用途。
- 方案二：先生成相同格式的两组三句和中译，再调用现有 `generateSentenceMetadata` 补分类和用途。
- 两种方案复用当前生成和分类提示词，不使用历史版本较短的规则。当前脚本的模型均为 `mimo-v2.6-flash`，关闭思考；图片请求输出上限 4096，单独分类请求沿用 2048。下方 2026-09-27 的历史实测使用 `mimo-v2.5`，不能视为 Flash 的测速结果。
- 每种方案使用相同的 JPEG 字节、难度和风格。默认初级、平铺直叙，3 张图各 3 轮，共 9 对样本，最多 27 次真实模型调用。
- 串行执行，逐对交替先后顺序，每轮轮换图片顺序，避免同时请求引起额外争用。图片请求与分类请求各沿用 20 秒超时，不重试、不调用 Kimi。
- 记录句子可展示时间、完整结果时间、单独分类时间、token 用量和失败次数。保留模型文本，便于复查是否真正完成了所有字段。

这只是本机直连模型的对照，不部署函数、不访问 Supabase、不生成回忆、不扣 App 次数。会产生 MiMo API 调用费用。不含审核、图片上传、数据库、向量、学习主题匹配，不能直接当作 App 的端到端耗时。

## 本机运行

在被 Git 忽略的 `.env.benchmark.local` 填写 `MIMO_API_KEY` 和 `MIMO_BASE_URL`。后者使用完整接口地址 `https://api.xiaomimimo.com/v1/chat/completions`，已于 2026-09-27 按 [MiMo 官方文档](https://mimo.mi.com/docs/zh-CN/api/chat/openai-api) 核对，不是只有域名的 base URL。不要把密钥传到命令行、聊天或 Git 中。

样图使用项目已有咖啡馆、户外徒步、儿童图片，副本压缩到最长边 512px、JPEG 质量参数 7、每张小于 45KB。与客户端的图片大小预算接近，但 macOS 与 iOS 编码器不完全相同；两种方案使用的字节严格一致。样图位于被 Git 忽略的 `tmp/mimo-generation-benchmark/`，可自行传入其他压缩 JPEG。

```bash
deno run --no-lock --allow-read --allow-write=tmp/mimo-generation-benchmark --allow-env=MIMO_API_KEY,MIMO_BASE_URL --allow-net=api.xiaomimimo.com --env-file=.env.benchmark.local scripts/benchmark-generation-metadata.ts --rounds 3 --level 简单 tmp/mimo-generation-benchmark/cafe.jpg tmp/mimo-generation-benchmark/hiking.jpg tmp/mimo-generation-benchmark/child.jpg
```

检查输入和提示词，不消耗模型用量：

```bash
deno run --no-lock --allow-read scripts/benchmark-generation-metadata.ts --dry-run tmp/mimo-generation-benchmark/cafe.jpg tmp/mimo-generation-benchmark/hiking.jpg tmp/mimo-generation-benchmark/child.jpg
deno test --no-lock --allow-read scripts/tests/generation-metadata-benchmark.test.ts
```

完整结果默认写入 `tmp/mimo-generation-benchmark/results.json`。再次运行可用 `--output tmp/mimo-generation-benchmark/another-run.json` 保留旧报告。

## 读数注意

- `sentenceReady`：句子已经返回并通过校验；分步方案不需要等分类完成。
- `allResultsReady`：句子、分类、用途全部完成；分步方案包含两个顺序请求。
- `pairedAllResultsReady`：只比较同图同轮两种方案都成功的样本。
- 中位数、平均值仅统计相应成功样本。必须同时看失败次数；超时意味着完成时间未知，不能将失败请求的较短耗时当作成功速度。
- 固定的是输入和规则，不是输出句子；模型每次生成的句长、分类和用途长度仍可能不同。
- 9 对样本是小样本对照，不代表长期稳定延迟。缓存命中、网络和服务负载都可能影响结果。脚本不预热额外请求、不人为关闭服务端缓存。

## 2026-09-27 实测结果

以下历史实测包含当时仍在生成的照片级 tags；之后已取消这一字段，当前脚本跟随业务代码不再请求或校验它。历史数据未修改，不代表取消标签后的重新实测。

北京时间 08:26:48 至 08:30:58，本机通过官方接口完成了上述 9 对、共 27 次真实请求。原始数据和生成文本保存在 `tmp/mimo-generation-benchmark/results-20260927.json`。本次没有修改业务数据库或部署线上函数，样图仅随测试请求发送到 MiMo；密钥未写入日志或 Git。

**完整结果合并生成更快；先展示句子则分步更快。**

以下主表只比较双方同图同轮都成功的 8 对样本，确保统计口径一致：

- 同一口径下，合并生成完整结果平均少等 6.28 秒，耗时减少约 38.5%；8 对成功样本中，7 对合并更快，1 对分步更快。
- 分步方案展示句子平均提前 3.32 秒，耗时减少约 33%。如果算上补全失败但句子已成功返回的第 9 次，句子可展示的平均时间为 6.62 秒，中位数 6.67 秒。
- 合并成功样本平均用量：输入 2683 tokens、输出 446.5 tokens。分步完整成功样本两个请求合计：输入 3063.25 tokens、输出 653 tokens。输出内容不是逐字相同，不能据此认定固定节省比例或质量相同。
- 本测试验证的是接口输出结构，不是人工评估分类准确率、句子难度或内容质量。

### 产品取舍

2026-09-27 用户确认约 10 秒的模型请求耗时可以接受，选择合并生成句子、分类和用途；向量与主题匹配仍留在后台。减少句子展示等待则分步更有优势，这是明确的产品取舍，不是合并方案在所有指标上更快。两种方案均有失败且样本很少，不能用本次结果推断长期可靠性；也不能把本机模型请求耗时直接替代 ECS 上或 App 全链路的耗时。

以上数据是合并改造前的真实测试快照，并未用新代码重新测量或覆盖。测试脚本现直接使用合并后的业务提示词，再移出元数据规则构造分步对照；两者的分类语义仍一致，JSON 占位示例随业务代码变化。后续复测应另存报告，不混入本次统计。实施和部署见 [生成链路](generation-enrichment.md)。
