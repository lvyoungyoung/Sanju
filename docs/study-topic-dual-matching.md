# 学习主题匹配与范围设置

## 当前规则（2026-09-23 更新）

- 预定义推荐名称和用户手动输入名称统一使用语义匹配；收藏仍独立按收藏状态选句，不提供匹配范围设置。
- 直接把主题名称（仅去首尾空格）送到 embedding 接口，使用 `query` 类型。不调用 MiMo 解释主题，也不区分 broad/specific。
- 每个句子可有两个 `document` 向量：原句（英文及中文翻译）和表达用途。两路均使用现有 `qwen3.7-text-embedding`、1024 维。
- 当前入选条件是：`用途相似度 >= 主题阈值 AND (原句相似度 >= 主题阈值 OR 所属分类相似度 >= 主题阈值)`。分类不能绕过用途要求，原句或分类单独匹配均不能入选。
- 分类向量以 `photo-life-v1` 版本和相同 embedding 模型缓存在 `learning_topic_embeddings`，环境内共享。只比较句子实际的 `learning_topic_ids`，有多个分类取最高相似度。分类缓存缺失时创建/首次准备会补齐，不再进行额外的主题意图提取。
- `match_source` 为 `semantic_both`（原句和用途）、`purpose_category`（分类和用途）、`semantic_all`（三路都符合）。旧 `learning_topic_id` 只保留作历史元数据，不再决定选句。
- 每个主题在 `study_scenes.match_threshold` 保存自己的阈值，默认 0.42。客户端七档从左到右为 0.48、0.46、0.44、0.42、0.40、0.38、0.36；左侧更严格，右侧更宽松。三路使用同一个阈值，数值不代表准确率。
- 创建、全量刷新和新增句子匹配都使用同一个数据库候选函数，检查主题、句子和向量的所属用户，以及 embedding 模型一致性。

## 生成与存储

MiMo/Kimi 原有图片生成请求中，要求每句额外返回 `expression_purpose`：一条不超过 30 个英文单词、240 个字符的表达用途。它必须来自句子本身，保留关键对象、动作、感受和限制，不从照片补入未表达的信息，不只是大分类或原句翻译。两组各三句及旧版三句格式都适用。

例如：

- `The lake reflected the snow-covered mountains.` -> `Describing a lake reflecting snow-covered mountains.`
- `We enjoyed a delicious meal by the lake.` -> `Sharing an enjoyable meal beside a lake.`

原句和用途分两批并行生成向量，每批最多当前生成的 6 句；响应按照 provider 的 `text_index` / `index` 重排，防止句子和向量错位。单批失败不丢弃另一路成功结果。生成式 AI 不增加额外调用，但 embedding 输入量增加。

登录用户保存在 `sentence_embeddings`：原有 `embedding`、新增 `expression_purpose` 和 `purpose_embedding`。匿名用户使用 `guest_sentence_embeddings` 的同名字段，按稳定的服务端句子 ID 暂存，登录上传本地回忆后迁移到账号，支持先上传回忆或先写入向量两种顺序。首次匿名生成响应不再替换已有合法句子 ID；恢复接口原本就保留 ID，无需修改。

用途缺失或格式错误时，不为了元数据丢弃已生成的合法句子，只记录缺失日志。向量索引仍在成功生成事务之后进行，保持原有非阻断设计：provider/数据库故障可能使一条或两条路线暂缺，不能承诺每次生成一定写入两套向量。缺少用途向量或用途文本的句子不能加入语义主题，但仍可在回忆、收藏中使用。原句向量缺失时，可由分类匹配补充，但用途仍必须达标。不伪造向量。

## 兼容与现有数据

- 详情页右上角提供匹配范围弹窗，滑动松手后保存，支持恢复默认；读取设置时不会重置已保存的范围。
- 不改生成最终提交、扣次数或恢复状态机，不增加扣次操作；学习记录和收藏不删除。
- 已有无用途的句子暂不参与自定义主题的语义匹配，不自动批量调用 AI 补齐。
- 调整范围和重新匹配在同一数据库事务中完成，失败时整体回滚。按主题行加锁，新句子增量匹配也读取对应主题的持久化阈值；不删除句子、收藏或学习记录。
- 已有主题首次打开时，如果缺少名称向量或尚未切换为新规则，客户端通过 `create-study-scene` 的 `prepare_only` 模式准备并重新匹配。按已授权的主题 ID 更新，保留 ID、创建时间、阈值和学习进度，不会重建已删除主题。完成后不再每次调用此准备接口。
- 已有主题的向量可能来自上一版本的 AI 意图。再次提交同名主题会用原始名称重算向量，保留主题 ID、创建时间和学习记录；迁移本身不访问外部模型。
- 旧创建 RPC 的参数及八列返回结构保持不变。`scope`、`search_description` 不参与当前入选。旧版只学习收藏的客户端无需更新。

## 发布顺序

1. staging 运行 Backend Database，按顺序部署 `20260923004000_add_per_scene_match_threshold.sql` 和 `20260923005000_unify_study_scene_category_matching.sql`。
2. 部署 `create-study-scene`，含同目录的 `categories.ts`。无需新环境变量或代理配置，使用已有百炼 embedding 地址和密钥。
3. 本次无需重新部署 `generate-memory-v2`、`recover-guest-generation`，双向量生成的前置版本需已部署。
4. 重新运行客户端，创建推荐主题和手动命名主题，确认都有范围设置；松手后显示更新状态和匹配数量，列表刷新期间保留原内容。
5. 验证跨设备读到同一阈值、新句子遵循各主题阈值、恢复默认、失败回退和不同主题相互独立。staging 确认后再部署同一版本到 production。

本地检查包括 PostgreSQL 实际执行的迁移/匹配/权限/匿名迁移测试，以及生成接口、原始主题输入、用途解析、向量乱序和单路失败测试。没有以测试替身替代真实模型匹配质量验证。

## Xcode 匹配诊断

部署 `20260923002000_add_study_match_diagnostics.sql` 后，用 Xcode Debug 运行客户端，打开主题详情或下拉刷新，在控制台筛选 `[StudyMatch]`。新建主题进入详情时也会输出。不需要重新部署 Edge Function 或修改代理。

日志包含主题名称、保存的阈值、查询向量模型、历史解释文本，以及原句、表达用途、原句/用途/所属分类三路相似度、是否实际入选和入选来源。`storedSource` 是数据库已保存的关联来源，`currentSource` 是按当前规则重新计算的来源；`linkMismatch=true` 表示现有入选状态与当前规则不同。它只是诊断，不会修复关联或重新生成向量。当前规则标签为 `purpose_and_sentence_or_category_v1`。

- `original` / `purpose` 分别是两路余弦相似度，不是准确率。`n/a` 表示无法计算，例如没有向量、模型不一致或用途缺失。
- `legacySearchDescription` 用于发现旧版主题解释的残留，不能单凭为空就证明向量曾按新规则生成。
- 新规则下预定义主题和手动命名主题都按上述三路规则诊断；旧规则的诊断兼容仍保留。
- 每次最多输出 100 条，优先已入选句子，再按最高相似度降序，末尾同时有总量与截断标志。未出现的句子不代表不存在。
- 只读 RPC 根据当前登录身份限制主题和句子所有权，不返回原始向量、密钥或其他用户内容。客户端仅 Debug 编译此请求和日志，Release 不调用；诊断失败或超时不影响详情加载。
- 日志含用户句子和用途，分享排查日志前请检查其中是否有私人内容。
