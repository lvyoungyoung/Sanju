# 自定义学习主题的双路语义匹配

## 规则

- 预定义主题保持按照句子的 `learning_topic_ids` 精确匹配。
- 自定义主题先用现有 MiMo 调用解释主题意图，返回英文 `search_description` 和 `match_scope`。
- `broad` 仅用于没有限制的宽泛生活主题，例如“描述风景”。同一个主题向量分别与句子向量、分类说明向量比较。
- `specific` 用于具体对象、动作、属性、地点或排除条件，例如“雨后的山间风景”。意图解析失败或返回旧格式时也默认为 `specific`。
- 句子相似度门槛保持 0.42。分类候选门槛初始设为 0.55，只保留与最佳分类分数相差不超过 0.08 的前两个分类。分类门槛与句子门槛相互独立，这些是待真实样本校准的工程初值，不是准确率保证。
- 宽泛主题：句子匹配或所属分类匹配，任一路符合即可加入。具体主题：必须先满足句子匹配，分类最多提供 0.03 的排序加分，不可绕过限制。语义匹配本身仍不能严格验证所有语言条件。
- 分类匹配允许补入尚无句子向量、但已有分类的句子。没有分类和没有有效句子向量的句子不会被猜测加入。
- 不恢复 AI 逐句复核，不改变学习次数、SRS、收藏、生成扣次或恢复流程。

## 向量与缓存

`learning_topic_embeddings` 保存 21 个分类的英文说明向量，使用现有 `qwen3.7-text-embedding`、1024 维、`document` 类型。与句子向量保持相同模型。分类说明定义在 `create-study-scene/categories.ts`。

缓存以分类 ID、模型、`photo-life-v1` 版本为键，全用户共用，仅 service role 可访问。自定义主题首次创建时按需补齐，最多三批并行请求；以后复用。首次初始化或并发冷启动可能增加延时和少量向量调用，失败只记录警告，匹配仍可使用已有缓存和句子向量。修改分类说明时须同时提升 TypeScript 和 SQL 中的版本。

创建主题、全量刷新、生成新句子后的匹配，共用 `semantic_study_scene_candidates`。新增/修改句子分类时触发匹配，无需等待该句向量；随后现有生成函数保存句子向量并调用增量匹配，规则一致。所有查询均校验主题、回忆和向量的所属用户。

## 旧主题与兼容

旧主题默认 `specific`，迁移不猜测其意图、不批量调用模型。要让已有的宽泛自定义主题使用分类补充，可以再次提交相同名称；会更新同一个主题，保留 ID 和学习记录，不需先删除。

旧 `create_study_scene_with_embedding` RPC 的参数和八列返回结构保留。新的上下文 RPC 是独立名称，避免 PostgREST 重载歧义。主题数量仍受数据库 20 个上限保护。只学习收藏的旧客户端不需要更新。

## 部署与验证

1. 先在 staging 执行 `20260923000000_add_category_semantic_study_matching.sql`。
2. 再部署 `create-study-scene`。无需新增环境变量，继续使用现有 MiMo / DashScope 配置。
3. 不需要重新部署 `generate-memory-v2`、`recover-guest-generation`，也不需要修改 Nginx。
4. 用已有风景句子创建“描述风景”，检查具体风景句是否被补入。再创建“雨后的山间风景”，检查没有因分类路线混入普通风景句。
5. 生成新的相关照片，验证句子自动进入主题。验证不同账号、收藏学习进度和预定义主题未改变。
6. 部署后运行旧客户端兼容检查；staging 验证完成后，再将同一版本部署到 production。

本地回归涵盖意图解析、缓存复用/失败、批次顺序、PostgreSQL 双路匹配、权限隔离、旧 RPC、20 个上限、学习记录保留和迁移重复执行。未通过测试替身声称真实模型语义效果已经验证。
